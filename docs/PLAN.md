# Family LINE Bot 設計書

## 操作

家族の LINE グループで、Bot 宛てメンション付きの文章からタスクと通知設定を操作する。操作結果と曖昧な対象の候補はテキストで返す。明確な登録・変更・完了・削除は即時処理し、削除データは復元できる。通常会話は無視し、同じ送信者が候補を選ぶ `#番号` と、Bot 通知への完了表現による引用返信を例外とする。メンションだけで使い方を表示する。

## リクエスト処理

1. Hono が LINE の署名を生の本文に対して検証する。グループと送信者を署名済みイベントから取得し、`isSelf` とメンション範囲で Bot 宛て本文を抽出する。
2. Workers AI が文章から単一の Intent と引数を抽出する。関連する作成と通知設定は一つの操作に含める。単一操作で表せない依頼は追加情報を求める。AI に渡すのは Bot 宛て本文と JST の基準日時で、会話履歴や DB の権限は渡さない。
3. 厳密な Zod スキーマで出力を検証する。対象は D1 で同じグループのタスクに解決する。明示の `#番号` を要求し、複数候補は同じグループ・送信者が10分以内に選ぶ。直近タスクの参照にも10分の文脈を使う。
4. Action Dispatcher が共通のタスク操作を実行する。D1 のバッチで `processed_events` と変更を確定し、同じイベントの再配送による二重更新を防ぐ。タスクの更新と通知設定はバージョンを確認して反映する。
5. Webhook には署名検証後に HTTP 200 を返し、推論と返信は `waitUntil` で処理する。返信の失敗は操作を巻き戻さず、ユーザーは一覧で結果を確認できる。

Bot 通知の引用返信は AI を経由しない。Push API の `sentMessages[].id` を精度を落とさず文字列で保存する。署名済み Webhook の `quotedMessageId` とグループが通知履歴に一致し、完了表現だけを含むときに、共通の完了操作を実行する。

## 通知スケジュール

- `tasks` に論理削除時刻、通知ルール、通知の有効フラグ、バージョン、計算基準、UTC の次回時刻を保存する。ルールは既定、明示した相対日の時刻、または曜日・日間隔・複数時刻による繰り返し。既定は期限まで8日以上なら7日前と前日、短ければ前日の20:00 JST。予定は未来に限る。
- `group_reminder_defaults` は今後の登録に使う既定値を持ち、既存タスクは登録時に取得した設定を保持する。`task_contexts` は直近のタスクID、操作、有効期限と、選択待ちに必要な構造化引数だけを持つ。
- 毎分の Cron は次回時刻に達したタスクを取得する。タスクと予定時刻が一意な `reminder_occurrences` に、初回送信前に本文と Retry Key を保存し、同じ D1 バッチでタスクを次の予定に進める。予定を一括生成しないため、長期タスクも同じ仕組みで扱える。
- 送信権の取得は D1 の条件付き更新で行い、試行回数で結果の上書きを防ぐ。送信権は2分、送信タイムアウトは10秒。5xx・通信エラー・タイムアウト・429・結果不明の中断は同じ本文とキーで再試行する。最大4回、予定から1時間か JST の日付境界の早い方で終了。429 は `Retry-After` と最低15分を尊重する。LINE の受理済みを示す409は成功にする。端末への配信は保証されない。
- ルールや状態の変更で古いバージョンの送信権取得を止める。送信中のリクエストと受理済み履歴は残る。送信済みメッセージ ID を LINE が返さない場合は引用による完了を特定できない。
- `0004` で既存タスクを移行し、登録日を基準に次の未来の予定から開始する。`notification_batches` は旧通知の履歴として保持し、旧 Cron の送信は終了する。`interaction_sessions` の旧ボタン操作は無効となる。

## 検証と運用

- Vitest で時刻計算と JSON 検証を確認し、ローカル D1 とモック API で Webhook、状態遷移、二重送信、失敗からの復旧を検証する。
- GitHub Actions は `npm ci`、型チェック、Vitest、Wrangler dry-run を実行する。LINE Secrets はローカルの `.dev.vars` または Workers Secrets に置く。ログにはイベントID・タスクID・処理段階・HTTP ステータスなどを残し、ユーザーの文章、通知本文、秘密値は記録しない。
- 実機確認はテスト用 LINE グループで行う。本番 Worker・D1・LINE の設定変更は対象と範囲を示し、明示的な承認を得て実施する。

## GitHub 運用

Issue → 作業ブランチ → 小さなコミット → PR → CI → ユーザーレビュー → Squash merge。最新 `main` から `<type>/<issue-number>-<slug>` のブランチを作成し、英語の Conventional Commits を使う。PR には概要、変更点、テスト結果、手動確認、未解決事項、関連 Issue を記載する。レビュー前のマージと CI からの本番デプロイは行わない。
