# Family LINE Bot 設計書

## 操作

家族の LINE グループで、Bot へのメンションか、同じグループで Bot が送信したメッセージへの引用返信からタスクと通知設定を操作する。明確な操作は即時処理する。曖昧なら候補か必要な1項目を質問し、同じグループ・送信者の回答を10分間受け付ける。通常会話と他人への引用は推論に送らない。メンションだけ、または「使い方」「ヘルプ」で案内を表示する。

## リクエスト処理

1. Hono が Webhook の署名を検証する。`isSelf` とメンション範囲で操作対象を抽出し、署名済みのグループ・送信者・イベントID・時刻と必要な入力を D1 の `webhook_inbox` に保存する。保存が成功したら200、失敗時は503を返す。受信を複数バッチに分けた場合も、イベントIDの一意制約で先に保存できたイベントを重複登録しない。
2. Webhook 後の `waitUntil` と毎分の Cron が Inbox を処理する。1回に最大4グループを並行で処理し、各グループは最大2件。Webhook のバックグラウンド処理と各 Cron 起動はそれぞれ25秒の共通期限を持つ。推論上限に3秒を加えた余裕がなければ新しい操作を始めない。推論と LINE API の上限は `AI_TIMEOUT_MS` と `LINE_TIMEOUT_MS` で個別に短縮でき、残り時間でも制限する。Cron の Inbox、Outbox、予定リマインダーは同じ期限のもとで並行実行する。期限に達したら待機を終了する。発行済みの D1 呼び出しは取り消せないため、確定の有無は永続化された行と処理権で判断する。
3. 同じグループの未確定操作は LINE の `timestamp`、同値なら D1 の受信連番順に処理する。条件付き更新で先頭の操作だけに45秒の処理権を与える。グループ内で先に新しい操作が確定した場合は、遅れて到着した古い操作を終了する。LINE がまだ配送していないイベントや、同じ時刻に発生したイベントの送信順は復元できない。イベントIDは重複判定に使う。
4. Workers AI が単一の Intent を抽出し、Zod で検証した結果を Inbox に保存する。タスクの特定と操作は同じグループに限定し、曖昧な候補の選択と直近文脈もグループ・送信者単位で処理する。D1 バッチで処理権と確定済み順序を検証し、タスク・通知・文脈の変更、`processed_events`、Inbox 完了、グループの確定済み順序をまとめて確定する。タスクのバージョン検証も維持する。
5. Inbox は `queued` → `running` → `succeeded` または `failed` と遷移する。一時的な推論・D1 障害は15秒・60秒以上待って最大3回、受信後15分以内に再試行する。処理権の期限切れは Cron が拾う。永続化済み Intent は再試行時に再利用する。不正出力・古い操作は終端失敗とし、終端時に入力とトークンを消去する。`succeeded` は操作処理の確定を示し、候補や対象なしの案内も含む。
6. 操作の確定と同じ D1 バッチで、イベントIDごとに1件の `operation_result_outbox` を保存する。通知先は署名済み Webhook のグループを使う。受信から50秒およびイベント発生から19分50秒のうち早い方まで、送信時間を確保できる場合に Reply を使う。期限不足、明示的な4xx拒否（408を除く）、AI の最終失敗は Push の対象とする。結果不明の操作には一覧の確認を案内する。
7. Outbox は Reply と Push の処理権を条件付き更新で45秒確保する。Reply 成功で通知を確定し、通信失敗・タイムアウト・送信中断などで受理が不明なら `uncertain` で終了する。Push は保存済み本文と同じ Retry Key で1時間以内に最大4回、429 は最低15分または `Retry-After` まで待って再試行する。受理済み409も成功として記録する。終端時は通知本文と返信トークンを消去する。通知処理はタスクを変更しない。LINE の受理から端末への配信までは保証できない。

Webhook 内で推論を待つ方式は、通常の推論や複数イベントで LINE の応答待ち時間を超えやすい。D1 Inbox は入力の永続化と実行を分離し、Workers・D1・既存 Cron で順序制御と復旧を行う。`0005` は `webhook_inbox` と `webhook_group_progress`、`0006` は操作結果の Outbox を追加する。操作と通知の障害は両テーブルの `event_id` で照合する。

Reply と Push の `sentMessages[].id` は精度を落とさず文字列で保存する。`0007` は Outbox に `line_message_id` と `task_id` を追加する。リマインダーは既存の履歴を利用する。署名済み Webhook の `quotedMessageId` を同じグループの送信済み行と照合する。対象がある引用の完了表現は AI を経由しない。その他の引用は対象のタスク名と期限だけを文脈として推論に渡す。引用と本文の名前が矛盾する場合や一覧のように対象のない引用では、操作者の意図を確認する。ID を保存できない場合は引用元を推測せず、送信失敗で確定済みのタスク操作を再実行しない。

日本語の Intent プロンプトは通知の追加・削除・置き換え・時刻変更を区別する。対象の名前は本文の表現に根拠がある場合だけ受け取り、正規化した名前の候補をグループ内で確認する。近い名前が複数あるときは選択を案内する。モデルの出力は Zod と対象照合で検証し、更新は TypeScript が実行する。

## 通知スケジュール

- `tasks` に論理削除時刻、通知ルール、通知の有効フラグ、バージョン、計算基準、UTC の次回時刻を保存する。ルールは既定、明示した相対日の時刻、または曜日・日間隔・複数時刻による繰り返し。既定は期限まで8日以上なら7日前と前日、短ければ前日の20:00 JST。予定は未来に限る。
- `group_reminder_defaults` は今後の登録に使う既定値を持ち、既存タスクは登録時に取得した設定を保持する。`task_contexts` は直近のタスクIDと、有効期限付きの候補選択または確認待ちの依頼を持つ。
- 通知の差分は純粋関数で合成する。既定値はタスクの計算基準に従って展開し、繰り返しには相対日の追加枠と除外枠を任意で持てる。重複枠は1件にまとめる。削除対象が曖昧なら質問し、最後の1件を削除する場合は直前のルールを残して停止する。
- 毎分の Cron は次回時刻に達したタスクを取得する。タスクと予定時刻が一意な `reminder_occurrences` に、初回送信前に本文と Retry Key を保存し、同じ D1 バッチでタスクを次の予定に進める。予定を一括生成しないため、長期タスクも同じ仕組みで扱える。
- 送信権の取得は D1 の条件付き更新で行い、試行回数で結果の上書きを防ぐ。送信権は2分、送信タイムアウトは10秒。5xx・通信エラー・タイムアウト・429・結果不明の中断は同じ本文とキーで再試行する。最大4回、予定から1時間か JST の日付境界の早い方で終了。429 は `Retry-After` と最低15分を尊重する。LINE の受理済みを示す409は成功にする。端末への配信は保証されない。
- 追加・部分削除で引き続き有効な再試行は、同じ本文・Retry Key・試行回数で次のバージョンに引き継ぐ。対象外になった枠の送信権取得は止める。送信中のリクエストと受理済み履歴は残る。
- `0004` で既存タスクを移行し、登録日を基準に次の未来の予定から開始する。`notification_batches` は旧通知の履歴として保持し、旧 Cron の送信は終了する。`interaction_sessions` の旧ボタン操作は無効となる。

## 検証と運用

- Vitest で時刻計算と JSON 検証を確認し、ローカル D1 とモック API で Webhook、状態遷移、二重送信、失敗からの復旧を検証する。
- GitHub Actions は `npm ci`、型チェック、Vitest、Wrangler dry-run を実行する。LINE Secrets はローカルの `.dev.vars` または Workers Secrets に置く。ログにはイベントID・タスクID・処理段階・HTTP ステータスなどを残し、ユーザーの文章、通知本文、秘密値は記録しない。
- 実機確認はテスト用 LINE グループで行う。本番 Worker・D1・LINE の設定変更は対象と範囲を示し、明示的な承認を得て実施する。

## GitHub 運用

Issue → 作業ブランチ → 小さなコミット → PR → CI → ユーザーレビュー → Squash merge。最新 `main` から `<type>/<issue-number>-<slug>` のブランチを作成し、英語の Conventional Commits を使う。PR には概要、変更点、テスト結果、手動確認、未解決事項、関連 Issue を記載する。レビュー前のマージと CI からの本番デプロイは行わない。
